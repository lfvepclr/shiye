**S0 结论**

1. **本机编译完全正常**，`cargo build` / `cargo test` 均通过。之前拉不到依赖是**全局 `~/.cargo/config.toml` 里配了已废弃的 rsproxy git 索引**（`https://rsproxy.cn/crates.io-index/`），仓库内新增 `.cargo/config.toml` 用 `sparse+https://rsproxy.cn/index/` 覆盖即可（与 Phantom 项目同一做法）。
2. 目标主机 x86_64 + Alpine 3.18.3，SSH 免密可用；但**没有 cargo、没有 swap、可用内存约 460MB** → 不在服务器上编译，只跑二进制。
3. 交叉编译**必须带 C 工具链**：`cargo build --target x86_64-unknown-linux-musl` 配 `linker = "rust-lld"` 会在 `libsqlite3-sys` 处失败（`cc-rs` 找不到 `x86_64-linux-musl-gcc`）。原因是我们依赖树含 C：SQLite 的 bundled 源码，后续 `reqwest`+`rustls` 还会引入 `ring`/`aws-lc-rs` 的 C 与汇编。
   → 采用 `cargo zigbuild`（zig 的 `cc` 能产 musl 目标码）。
   → Phantom 之所以只用 `rust-lld` 就够，是因为它刻意保持纯 Rust 依赖（TLS 用 RustCrypto 而非 ring，存储无 SQLite）。
4. 主机**没有 Caddy** → S8 需先装（`apk add caddy` 或官方静态二进制）。

**验收**：`git log` 有一条 commit，`git remote -v` 指向 origin，`~/.workbuddy-ai/skills/harmonyos-development/SKILL.md` 存在。

### 2026-10-18 · 页序 / 裁剪擦除 / 百度接入

**1. 页序无法调整（根因）**

`http.RequestMethod` 枚举里**没有 PATCH**（只有 OPTIONS/GET/HEAD/POST/PUT/DELETE/TRACE/CONNECT）。客户端传 `http.RequestMethod.PATCH` 得到 `undefined`，NetStack 退化成 GET，并把 JSON body 拼进 query：

```
GET /shiye/api/v1/groups/{id}?{"page_order":["…"]} HTTP/1.1
```

`{`、`"`、`[` 不是合法 request-target，hyper 在进入路由前就以空 body 400 拒绝，所以客户端只能显示 `HTTP 400`。修复：

- 客户端 `patchGroup` 改用 `PUT`；服务端 `/groups/{id}` 同时挂 `put(groups::patch)`（语义与 PATCH 相同）。

### 2026-10-18 · 分享链接打开显示「链接无效或已过期」

**根因**：Viewer 内部所有请求都是相对路径（`./state`、`./img/…`），而分享链接是 `/shiye/s/<token>`（无尾斜杠）。浏览器解析相对地址时会把最后一段当成文件名，于是 `./state` 变成 `/shiye/s/state` —— 404，前端 catch 后显示「链接无效或已过期」。`/s/<token>/` 这条路由当时也不存在，手动补斜杠反而 404。

**修复**：

1. `GET /s/{token}` 在路径不以 `/` 结尾时 `308` 到 `/s/{token}/`（`OriginalUri` 判断），并注册 `/{token}/` 路由。
2. Viewer 里加 `BASE = location.pathname`（自动补尾斜杠），把所有相对地址改成 `BASE + 'state' / 'img/…' / 'fig/…' / 'richtext/…'`，反代改写前缀也不会错。
3. `build_share_url` 直接产出带尾斜杠的规范地址，客户端复制与二维码少一次跳转。

**验证**：`/s/<token>` → 308 → `/s/<token>/` → 200；`/state`、`/img/<id>?v=thumb`、`/richtext/<id>` 全 200；Chrome 实测无斜杠与带斜杠两种写法都能正常渲染出 3 页 84 块。服务端 40 项测试全绿（同步更新了分享用例的断言）。

### 2026-10-18 · Word 版式与 Viewer 图文叠加

**1. Word 还原度（结论：做不到 100%，也不该承诺）**

Word 是流式排版，没有"绝对坐标"概念，原图的逐字位置无法照搬。当前做到与做不到的边界如下。

已做到：

- 页面 A4 + 版心 21×29.7cm、上下 2.54cm、左右 2cm；正文两端对齐、首行缩进 2 字符（`w:firstLine=440`）、1.5 倍行距
- 标题按 `#` 层级分 16/14/12pt，一级居中、段前段后间距；图注居中 9pt
- 插图宽度按 `bbox 宽 / 页宽 × 版心宽` 还原，高度不超过版心；表格内插图限高 1.5 英寸
- 表格：HTML `<table>` 与 PaddleOCR 的 **markdown 管道表格**都转成 Word 表格（`Table Grid`、居中、单元格垂直居中、首行加粗、单元格内可放插图）
- 行内 `$...$` → Unicode（△ ∠ ⊥ ≥ × ÷ ° 等），`\frac` 线性化为 `(a)/(b)`，上下标转 ⁰¹²/₀₁₂

做不到（明确记录，避免误期）：

- 逐字坐标/换行点还原；双栏、文字绕图、页眉页脚、页码不保留
- 公式不是 OMML 对象，而是 Unicode 近似——`\frac`、矩阵、多层上下标会退化
- 表格列宽由 Word 按内容自动分配，不还原原表列宽

顺手修掉的四个实伤：管道表格退化成一段带 `<img src="…">` 的乱码、`$...$` 原样输出、`#` 标题符号泄漏到正文、`&amp;` 等实体未解码。

**2. Viewer 原文视图改成图文叠加**

- 卡片 `aspect-ratio: 页宽/页高` 锁定比例，块用 bbox 百分比绝对定位
- 字号由单行块高度推算后写成 `--fs: N cqw`，配合 `container-type: inline-size`，窗口/图片怎么缩放都等比跟随；行高 1.85 对齐原图行距，单行块视觉上正好落在原行内
- 顶栏「原图」开关（localStorage 记忆），关闭后隐藏底图，只剩按原位置排布的文字，等于"识别结果即版面"
- 图片块直接叠 OCR 抠出的插图；表格块因浏览器中文最小字号（12px）限制，用"布局框放大 1.6 倍 + `scale(0.625)`"压回原尺寸
- 点击任意块仍是选择/复制，选择态与文本视图联动
